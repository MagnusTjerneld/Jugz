# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Jugz — an English-language water-jug puzzle game (three jugs, measure out an exact amount), shipped as an installable PWA. Zero runtime dependencies and no bundler; the only build steps are two Node generators that commit their output.

- `index.html` — the entire game: CSS, markup, and game logic in inline `<script>`
- `levels.js` — **autogenerated**, do not hand-edit; defines `const LEVELS`
- `generate-levels.js` — Node script that regenerates `levels.js`
- `sw.js`, `manifest.webmanifest`, `icons/` — the PWA layer (`icons/` is autogenerated)
- `generate-icons.js` — Node script that regenerates `icons/`
- `mockups/` — design drafts, opened straight in a browser; excluded from the published site
- `_config.yml` — Jekyll `exclude` list keeping dev files off the published site

All user-facing strings, comments, and identifiers are English. The game was originally written in Swedish and translated wholesale; keep new text in English.

## Commands

```bash
node check.js               # all offline checks; exits 1 on failure (CI runs this on every PR)
node smoke.js [base-url]    # checks the deployed site; waits for the deploy to catch up first
node generate-levels.js     # regenerate levels.js (overwrites it in cwd)
node generate-icons.js      # regenerate icons/*.png
python -m http.server 8000  # serve locally; needed to exercise the service worker
```

No package.json, no test runner, no linter. Opening `index.html` over `file://` works for gameplay, but the service worker will not register there — use a server to test anything PWA-related.

Do not use `convert` on this machine for image work: on Windows that resolves to the NTFS conversion utility, not ImageMagick.

## Architecture

**Shared BFS core, duplicated in two places.** Both `generate-levels.js` and the inline script in `index.html` contain near-identical `key()`, `pours()`, and a solver (`solve` / `solveFrom`). `pours()` defines the rules: pour from jug *i* into jug *j* until the source empties or the destination fills. If you change pour semantics, change both copies or the generator's difficulty ratings will no longer match what the game enforces.

**Level generation** (`generate-levels.js`):
1. `candidates()` enumerates every capacity triple `a>b>c` with `5≤a≤19`, runs BFS from `[a,0,0]`, and records the minimum move count (`opt`) for each reachable goal volume. Only puzzles with `opt≥2` qualify.
2. Candidates are bucketed by `opt` and shuffled with a **seeded** PRNG (`mulberry32`, `SEED=20260819`) so the level bank is reproducible. Changing the seed reshuffles all 150 levels and invalidates players' saved star data by index.
3. A difficulty curve is built from `base` (15 blocks of 10 levels, rising) plus per-position `offsets` giving breathers and spikes. Each target `opt` is filled from the nearest non-empty bucket, avoiding duplicate puzzles and the same capacity triple within the last 4 levels.
4. Every emitted level is re-verified by an independent `solve()` call; the script exits non-zero if any `opt` disagrees.

Each level is `{caps:[a,b,c], goal, opt}`. Start state is always `[a,0,0]`.

**Game state** (`index.html`): module-level `li, caps, state, history, moves, opt, goal, sel, busy`. Interaction is tap-to-select-source, tap-to-select-destination (`tap()`); `busy` gates input for 520 ms to match the CSS water transition. Star rating in `checkWin()`: 3 stars at `moves ≤ opt`, 2 at `≤ opt+2`, else 1. Undo decrements `moves` — it is an alternative to restarting, not a move of its own, so it must not count against the star threshold. The `history.length` guard keeps the counter from going negative.

**`opt` is withheld until the level has been cleared once** (`showOpt()`), because the optimal count is a substantial part of the puzzle: knowing "3 pours" narrows the search enormously. The header reads `Pours 4` on a first attempt and `Pours 4 / 3` afterwards. The label is deliberately a count of *performed* pours, not a budget — an earlier `Moves 0 / 3` read as an allowance. Two coarser leaks remain by design: the difficulty badge buckets `opt` into Easy/Medium/Hard, and the hint button reveals the next optimal move on demand.

**Persistence**: `localStorage` key `jugz_v1`, shape `{current, stars:{levelIndex:starCount}, skin}`. All access is wrapped in try/catch so a blocked/absent localStorage degrades to a playable-but-unsaved session. Level *n* unlocks when level *n-1* has ≥1 star (`unlocked()`).

`localStorage` is best-effort storage: WebKit clears script-writable storage after seven days without interaction, and Chrome evicts origins under disk pressure. `askPersist()` requests exemption via `navigator.storage.persist()` — but only once `PERSIST_AFTER` (10) levels have been cleared. Asking on first load is worse than useless: early requests are denied more often, and Firefox surfaces them as a dialog. Browsers decide by heuristic (installed PWA, engagement), so a denial is normal and not a bug — a cold Chrome profile on localhost denies it.

`askPersist()` queries `navigator.permissions.query({name:'persistent-storage'})` first and bails on `denied`. Be aware of what that does **not** buy: Chrome reports `prompt` while still refusing on heuristic grounds — measured on a cold profile, the state was `prompt` and `persist()` returned false anyway. The query only short-circuits an explicit denial. What actually keeps the console clean is `console.debug`, which lands on Chrome's Verbose level: visible when you look for it, silent otherwise. The permission name is unknown in some browsers and throws, so that call has its own try/catch and falls through to attempting `persist()` regardless.

Note the save is keyed by **level index**, so regenerating `levels.js` with a different seed silently reattributes stars to different puzzles. Nothing in code guards this. (The English translation deliberately left `SAVE_KEY` and the level data untouched, so existing players kept their stars.)

**Rendering**: jugs are hand-built SVG strings (`jugSVG()`) sized proportionally to capacity relative to the largest jug in the level. Water level is two synced rects — a filled `waterrect` and a `wclip` clip rect for the rising bubbles — plus a `surfg` group holding two drifting wave paths. Animation is pure CSS transitions/keyframes driven by attribute and `--custom-property` writes from `render()`; `fitJugs()` rescales the SVGs on resize to fit the stage. A `prefers-reduced-motion` block disables all of it.

The palette is a set of `:root` custom properties (`--night`, `--water-hi`, `--amber`, …); use those rather than literal colors.

**Skins.** A skin is a second block of the same custom properties under `html[data-skin=…]`, plus a row in each of the tables at the top of the script (`UNIT`, `VESSEL`, `VERB`, `BRAND`, `THEME`) and a vessel generator. There are three: the water, `wine` (*Winez* — red wine in stemware, measured in `U`) and `beer` (*Beerz* — a German stein of lager, measured in `S` for Seidel). `SKINS` is the order the hidden switch walks, so a fourth is a row in each table and an entry there; nothing else. The token names still say `--water-hi` and `--foam` on purpose — a skin redefines those properties, it does not rename them across the file. Five things do not follow from a straight swap:

- **`--on-primary`.** `button.primary` used a literal `#0B2B26`, which is legible on turquoise and roughly 2:1 on ruby. The dark/light choice has to be its own token.
- **Literal `rgba()` tints.** The difficulty badges and `.cell.done` mixed their own backgrounds from hardcoded channel values, which stayed turquoise after a swap. They are `color-mix()` off a token now, each preceded by the old `rgba()` line as a fallback for browsers without `color-mix`.
- **`--done`.** In the water skin the cleared-level cell is `--water-hi` on a teal card. In wine, ruby on burgundy is the same hue as the card behind it, so `--done` is the meniscus rose instead.
- **`--hint`.** The hint flash strokes the vessel, and it was `--amber` until the beer arrived — where an amber outline over amber beer is no flash at all. It is its own token now, cold in the beer skin: the one cue that must never be mistaken for the liquid, and white is already what a selected vessel turns.
- **`--amount`.** Every vessel shows two numbers on one line of sight — the capacity etched on the glass (`--etch`) and the live amount below it — and in the same lavender white they were read for each other. The amount now takes the colour of the liquid, so the moving number is the one that carries colour and the etched one stays part of the vessel. Ruby fails here for the same reason it fails for `--done`, so wine borrows the meniscus rose again. `render()` drives three states off it: `--gold` once the amount is the one asked for, `--amount` while there is liquid, `--haze` at empty. Beer is the awkward one of the three, because the liquid is *already* gold: there the goal state moves the other way instead, up into a pale foam-lit cream, rather than to a warmer gold nobody could tell from `--amount`.

`glassSVG()` and `steinSVG()` emit the same element ids as `jugSVG()` (`water<i>`, `wrect<i>`, `surfg<i>`, `clip<i>`), so `render()` never asks which skin is on — with one exception. It used to assume the liquid moves between `y=20` and `y=H-10`; a wine glass fills the **bowl only**, and that band would pour wine down into the stem. Every generator now publishes its band as `data-top`/`data-bot` on the `<svg>` and `render()` reads it. Any future vessel must do the same — the stein needs it too, for its own reason: `data-top` stops well short of the rim so the head has room to stand inside the glass.

Glass geometry: capacity drives bowl height, bowl width, belly bulge and stem length together, so the three glasses of a level differ by silhouette (port tulip → bordeaux → burgundy balloon) rather than only by size. Two details are load-bearing. The rim is an ellipse, not a line: the near half closes the bowl path, the far half is a separate faint stroke — without it the shape reads as a cone. And the rising bubbles are replaced by *legs*, three tears sliding down the wall above the surface; bubbles read as fizz, which is wrong for a still red.

Unlike the bubbles, the legs do not loop. `runLegs(i, was)` gives them exactly one run per pour, on the glass that was poured **out of** — the film is what the receding wine left behind, so the tears start at the level that glass was emptied from and run down to where it settled. A still red does not weep by itself, and the loop kept sending fresh tears down glasses nobody had touched in a minute. Four things this rests on. The band (old level minus new) is only knowable at pour time, so the SVG carries just the horizontal placing and the stagger, and `runLegs` writes `--ls` and `--lg`. Duration is derived from the band at a constant `LEG_SPEED`, because a fixed duration made a long drain race and a short one crawl. The legs hang off their own `legsg` group, not `surfg`: the surface group goes transparent when a glass empties, and a glass poured dry is exactly the one with the most wall to run down — `legsg` also carries no transition, since it must be parked at the new line before the run starts rather than sliding there with the level. And restarting the animation means the class has to leave and return with a forced reflow between, which is `getBoundingClientRect()` rather than the `offsetWidth` read used on the droplet, because `legsg` is an SVG `<g>` and SVG elements have no `offsetWidth`.

**The stein** (`steinSVG()`) is a dimpled Maßkrug: near-straight walls drawing in a little towards the base, and the same ellipse rim as the wine glass, near half closing the body path and far half a separate faint stroke. The handle is a fat round D (`html[data-skin="beer"] .glasshandle` thickens the stroke — a stein is carried by the fist, not by a thumb loop) that stands well off the wall but is **short and sits low**, gripping the bottom half of the mug: a handle reaching up to the rim is a jug's, and that is what it read as.

A ring is pressed round the neck a little below the rim (`.glassband`, its own class so it lights up with the vessel on select and on a hint), and the dimples start only a quarter of the way down — a Maßkrug is pressed from below that ring, and the smooth top is also where the head sits. The ring bows the opposite way from the far half of the rim and bows less, because it is a band wrapped round the mug seen from further below the eye. The dimples are laid out to a **count, not a pitch**: rows are spread evenly over the wall below that and the ring size follows from the spacing, because a fixed pitch left the small mugs with one or two rows while the big ones had six. Four rows is where the count starts, since one row is always given up to the capacity mark, and every one of the 116 stein sizes in the level bank keeps at least three. The offset rows run off **both edges** and the silhouette cuts them: those half rings are what make the wall read as curved rather than as a panel of dots. Three more things are the stein's own. The bubbles come back: fizz is wrong for a still red and exactly right for a lager. The row that would fall across the etched capacity is skipped whole, leaving the smooth band a real Maßkrug carries its fill mark on — dimpling through the number is what made it hard to read, and giving up a slice of a row rather than all of it just looks like a mistake. And the beer arrives with a head.

The head hangs **inside** `surfg`, not beside it, so it rides the beer line with no help from `render()` — the opposite call from the wine legs, which need their own group precisely because `surfg` goes transparent on an empty glass, whereas a stein with no beer should have no foam either. What is scripted is only the surge: `runHead(i)` gives the head one run per pour, on the stein poured **into**, the mirror of the legs. A loop would be wrong for the same reason it was wrong for the legs — beer at rest does not re-foam. `transform-box:fill-box` is load-bearing: it puts the transform origin on the foam's own bottom edge, the beer line, so the head grows up into the glass; an SVG element's default origin is the middle of the viewBox, which would have the foam swelling out of the stein sideways. Restarting the animation takes the same class-off, forced-reflow, class-on dance as the legs, and the reflow is `getBoundingClientRect()` for the same reason.

The switch is deliberately hidden: three taps on the wordmark, each following the one before it within 900 ms. It walks `SKINS` in order rather than toggling, so three taps more carry on to the next skin and eventually back to the water; the droplet turns with it — it pours over into the wine and comes up round as a bubble of foam in the beer. A single tap fires by accident, and an entry in the level screen gives the joke away before anyone finds it. Three things that cost a release each to learn. The tap target is a `::after` laid over the wordmark, because the wordmark box hugs its own text — 81×31 px, with a 9 px droplet inside it — and aiming at a logo that size on a phone mostly misses; the overlay does not touch the layout. The counter is a chain rather than a fixed total window, because a window punishes exactly the person still working out that the logo does anything: they tap, look, tap, look, and the run expires under them. And the counter listens on **`pointerdown`, not `click`** — the wordmark deliberately carries no `cursor:pointer`, and iOS Safari withholds `click` from an element it does not read as clickable, so on a phone the switch was simply dead while every other tap target (`.jug`, `button`, `.cell`, all of which do have the pointer cursor) kept working. And a run of taps is only cleared once the swap actually happens: `swapSkin()` refuses while a pour or a previous wipe is running, and clearing regardless made the third tap vanish. From the second tap the droplet lights up — one stray tap does nothing, a repeat says keep going; without it the switch is not merely secret but undiscoverable. A circle of the incoming backdrop grows out of the droplet, the skin changes underneath it, then it fades — one gesture instead of a hundred cross-fading properties; `prefers-reduced-motion` skips it and swaps instantly. The choice is persisted as `save.skin` and `<meta name="theme-color">` follows it, but **title, manifest, icons and `og:image` stay Jugz** — a skin nobody can see from the outside stays secret, and that is also why `check.js` needs no changes.

## PWA layer

The site is deployed to GitHub Pages at `/Jugz/`, a **subdirectory**, not a domain root. Every path in the PWA files is therefore relative (`./index.html`, `./sw.js`, `./icons/…`) — an absolute `/…` path would break in production while still appearing to work on a root-served local server. Test under a subpath (serve the parent directory) when touching paths.

`sw.js` keeps two caches: `jugz-shell-<VERSION>` precached at install from `SHELL_FILES`, and `jugz-runtime-<VERSION>` holding the Google Fonts CSS and woff2.

Navigation requests are answered from the cached `./index.html` regardless of URL, which is what makes the game start offline.

### How a release reaches users

Correctness does not depend on anyone remembering to bump a version. Two independent paths carry an update:

1. **Content-only release** (`sw.js` untouched). The navigation races the network against `NAV_TIMEOUT` (2 s), so a visitor on a working connection gets the new `index.html` on *this* load. Subresources (`levels.js`, icons) stay stale-while-revalidate and are therefore one load behind.
2. **Release that changes `sw.js`.** The browser byte-compares the script and installs a new worker. Because a controller already exists, the page shows the "New version available / Reload" pill; clicking it posts `SKIP_WAITING`, and the `controllerchange` handler reloads.

Why the navigation is not plain network-first: `fetch` against an unreachable host can hang for a long time before rejecting, which would stall a launch that could have been served entirely from cache. The race caps that at `NAV_TIMEOUT`. A `self.navigator.onLine === false` fast path skips the race entirely when the browser knows it is offline — measured without it, a dead server cost the full 2 s on every launch. The check is written as `=== false` so an absent API degrades to the race rather than to a wrong branch.

Consequence of (1): a release that changes `index.html` **and** `levels.js` can briefly serve new HTML against a cached `LEVELS`. Low risk here because `LEVELS` is plain data with a stable shape — but if the level format ever changes, bump `VERSION` in the same commit so the whole cache is discarded.

Two details that make this work, both easy to break:

- The page registers with `updateViaCache:'none'`, otherwise the HTTP cache can hide that a new `sw.js` exists.
- Revalidation fetches pass `cache:'no-cache'`. GitHub Pages serves `max-age=600`, so without this the SW would revalidate against the browser's own cache and see nothing new for ten minutes. Unchanged files answer `304`, so the cost is a conditional request.

Google Fonts are fetched once and never revalidated. The `css2` response names content-versioned woff2 URLs, and that pair keeps working indefinitely. (An earlier version claimed this in a comment while the code still background-fetched both on every load — a DevTools network log is what caught it.)

`VERSION` is now a manual escape hatch for discarding every cache wholesale (`activate` deletes any cache outside the current version's set), not the update mechanism. Still add new shell files to `SHELL_FILES`; forgetting only means the file is fetched from network rather than precached, not that users get stale content.

The `controllerchange` reload is gated behind a `wantReload` flag set by the button. `clients.claim()` in `activate` fires `controllerchange` on the very first install too, and reloading there would be a spurious refresh on a first visit.

`generate-icons.js` renders both the icons and `og-image.png` with a hand-rolled PNG encoder over the built-in `zlib` — no image dependency. `render(w, h, drops, bg)` is shared; `icon()` places one centered droplet, `banner()` three in falling sizes. The `bg` argument exists because the square icons and the 1200×630 banner need different gradient radii — changing it in one place silently alters the other, so the icon call passes the original `{rx:1.30, ry:0.90}` explicitly. Colors mirror the `:root` palette in `index.html`, so update both together.

## Link previews

Teams, Slack and friends read Open Graph tags. Two things they are strict about:

- **`og:image` must be an absolute `https://` URL.** A relative path yields a preview card with a placeholder instead of an image — this is the usual cause.
- The image must be publicly reachable, PNG/JPEG, ideally 1200×630.

The four absolute URLs in `index.html` (`og:url`, `og:image`, `twitter:image`) hardcode `https://magnustjerneld.github.io/Jugz/`. **If the site moves, they must be updated by hand** — nothing derives them.

Unfurl results are cached hard by these services. After changing tags or the image, an already-shared link often keeps showing the old card; sharing the URL with a throwaway query string (`?v=2`) forces a fresh fetch.

## Checks

There is no test framework and no `package.json`. Two dependency-free Node scripts cover what can be verified without a browser, wired to `.github/workflows/`:

**`check.js`** runs on every PR. It re-runs both generators *in a temp directory* — they read nothing and only write — and byte-compares the output against what is committed, so a generated file can never drift from its generator. It also re-verifies all 150 levels with an independent BFS, parses the inline script in `index.html`, and asserts that `SHELL_FILES` entries exist, `index.html` references resolve, `og:*` URLs are absolute `https`, PNG dimensions match the `sizes` declared in the manifest, and `_config.yml` excludes every dev file.

**`smoke.js`** runs after a push to `main`. It first waits until the deployed `index.html`, `sw.js`, `manifest.webmanifest` and `levels.js` are byte-identical to this commit — Pages builds asynchronously, so without this gate the checks race the deploy. Only then does it assert status codes, content types, and that dev files 404. Gating on all four files matters: an early version compared only `index.html` and reported green against a deploy whose `sw.js` was a release behind.

Two traps found while building these, both worth preserving:

- **Line endings.** With `core.autocrlf=true` on Windows, git checks out CRLF while the generators write LF, so the byte comparison failed on a clean checkout. `.gitattributes` pins the tree to LF, *and* `check.js` normalizes line endings for text files anyway (PNGs stay byte-exact). CI on Ubuntu would never have surfaced this.
- **Vacuous checks.** Every assertion here was negative-tested — break the thing, confirm it fails, restore. A check that cannot fail is worse than no check, because it reads as coverage.

What these do **not** cover: anything requiring a real browser. Service worker behaviour, offline start, the update pill, and layout were all verified by hand. Bugs found that way this cycle include the update pill covering the button row, `cacheFirst` never revalidating, and `fontCache` background-fetching despite a comment claiming otherwise. A Playwright smoke test would close that gap at the cost of the repo's first dependency.
